# Project: Stavební deník (construction site diary)

## Architecture (current stack)

- **Backend**: Kotlin 2.4, Ktor 3.6, jOOQ 3.21, Flyway 12, **PostgreSQL 18 only** (schema uses `uuidv7()`), Argon2id passwords, JWT in an HttpOnly cookie.
- **Frontend**: Vite 8, React 19, React Router 7, Tailwind CSS 4 (`frontend/`, its own pnpm workspace; `frontend/pnpm-lock.yaml` is committed and CI and the image build install with `--frozen-lockfile`, so a `package.json` that disagrees with it fails the build).
- **PDF export** (`GET /api/reports/{id}/pdf` by report id, `GET /api/projects/{projectId}/reports/{idOrDate}/pdf` by id or by day inside one project; a bare date on the first route is `400`, because dates repeat across projects and an entry of another project must never be exported by accident; an unknown entry is `404`):
  - The `typst` command-line tool (`0.15.1` in the Docker image and CI, pinned by SHA-256 checksum) renders the fixed template `backend/src/main/resources/pdf/report.typ`.
  - User text never becomes part of the template: it travels as JSON data (`data.json`) and is shown as plain text, so it cannot be executed as typst code.
  - Each export gets its own temporary directory, a 20 s timeout (the process is killed), and at most two exports run at the same time. A third waits for a free slot for at most 10 s and is then refused with `503`, `Retry-After: 10` and `code: PDF_BUSY`, so a burst of exports cannot hold request threads and browsers for minutes.
  - Without typst the endpoint answers `503` too (without that code); it never returns an empty PDF. The project page offers a PDF button for **every** entry in the list, not only the newest.
  - **What the document says** (backlog B8; the data is `ReportPdfData`, one section per builder function in `PdfExportService`):
    - Order: the title, **part A** (the identification of the diary, with the subcontractors and the supporting documents), **part B** (the entry), the signature with "Konec denního záznamu č. N", and then what was added after the signature (acknowledgements, addenda, entries of other parties, marked as not part of the signature; on a draft, which has no signature, an entry of another party stands under a neutral heading).
    - Part B prints the **content** the signature covers: the number, the author, the late-entry flag and reason, the control-day flag, the construction object, the weather, the workers with a total, the work description, the eight fields of `EntryDetails` and the photos (each with the SHA-256 of its file; the images themselves are not in the PDF). **Every heading is printed**, with "bez záznamu" where nothing was entered. Not everything the signature covers is printed: for a photo the id, the SHA-256 of the thumbnail and the uploader's id, and the project's id (the project is named by its name). And not everything printed is covered: the time a photo was uploaded, the names of the author, the uploader and the signer (read from the users as they are now) and the signer's ČKAIT number. A very long name or ČKAIT number of the signer is cut with an ellipsis in the signature block (the signature check shows it in full).
    - A signed entry whose hash or audit row is missing says so in words: in signature format 1 as an old entry (before hashes, or before the audit trail in test data), from format 2 on as a failure ("záznam nelze ověřit"), like `ReportSignature.check`.
    - The signature block (signer, time, entry id, the SHA-256 of the content, and the SHA-256 of the entry's `report.lock` row in the audit chain) is never split between two pages and is followed by "Konec denního záznamu č. N", the electronic form of striking out blank space (a draft says in words that it has no number yet). The audit row is printed so that the entry is tied to the chain (its `after` snapshot holds the content hash); **the head of the chain is not printed**, because it changes with every action and tells every reader how busy the whole company is. An entry with no `report.lock` row (signed before the audit trail existed, test data only) says so instead of failing.
    - A draft carries "KONCEPT – NEPODEPSÁNO" across every page. Every page has a footer: project, number (or "bez čísla"), date and "Strana X z Y".
    - Dates are Czech (`28. 9. 2026`, with the weekday for the day of the entry) and times are **Prague time with the zone** (`14:32:07 SELČ (UTC+2)`, `CzechFormat`), also the day the identification is "valid on" (decision D10). The API and the audit snapshots keep ISO dates and UTC.
- **Docker image** (`Dockerfile`):
  - **Base image:** Ktor + the built SPA + typst on a **glibc** (Ubuntu) Temurin JRE. It must not be Alpine: the password library `argon2-jvm` loads a native library through JNA, and on Alpine (musl libc) the JVM dies with SIGSEGV as soon as a password is hashed (creating a user). The application also hashes and verifies one throwaway password at startup (`PasswordService.ensureWorks`), so such a broken environment fails at deploy time, not at the first account creation.
  - **The application does not run as root:** the entrypoint (`/app/entrypoint.sh`, written by the Dockerfile) starts as root only to give the data volume (`/data/uploads`, root-owned when Fly mounts it) to the user `app`, then drops privileges with `setpriv` before the JVM starts; the CI boot test checks the process user and the owner of the photo directory.
  - **Memory:** `JAVA_TOOL_OPTIONS` caps the heap at 40 % of the machine (`-XX:MaxRAMPercentage=40`) and ends the process on an out-of-memory error (Fly restarts it); the rest is for what the heap does not hold: Argon2 (up to 4 x 64 MiB native), image decoding, class metadata, threads and the typst processes. `fly.toml` asks for a `shared-cpu-1x` machine with **1 GB** (Fly's default is 256 MB); change that value together with the percentage.
- **Testing**:
  - Backend: JUnit 5, Testcontainers `postgres:18-alpine`, Ktor `testApplication`, WireMock / MockEngine. Tests use a fake typst; `RealTypstPdfTest` runs the real tool and is skipped when typst is not installed (CI installs it and sets `REQUIRE_TYPST=1`, which turns a missing typst into a failure).
  - E2E: Playwright against the live stack (Ktor on :8080, Vite dev server on :5173 proxying `/api`), and in CI **also against the built production image** (`scripts/ci/e2e-image.sh`: image in `APP_ENV=production`, as the database role that owns nothing, schema migrated by the owner, the built SPA served by Ktor with its real security headers and secure cookies). The second run is what can see a broken production bundle, a Content Security Policy the SPA violates, a missing grant for the application's role or a file the non-root user cannot write.
- **Repository root**: only the Playwright suite (`e2e/`, `playwright.config.ts`, `scripts/dev/e2e-prepare.ts`) and the commit hooks (husky, lint-staged, prettier) live in the root `package.json`. The former Next.js + Prisma application was removed (2026-10-09); it is in the git history if anything is needed from it.

## jOOQ code generation

Generated classes live in `backend/src/generated/jooq` and are meant to be committed, so builds, tests and Docker/Fly builds never need a database.

```bash
./gradlew :backend:generateJooq   # starts postgres:18-alpine via Testcontainers, runs Flyway, generates Kotlin
```

Run it after every migration change and commit the result. CI job "jOOQ codegen drift check" regenerates the sources and fails the PR when they differ from what is committed (modified, added or deleted files); it uploads the fresh output as the `jooq-generated-sources` artifact.

To check for drift locally (needs Docker; empty output means in sync):

```bash
./gradlew :backend:generateJooq && git status --short backend/src/generated/jooq
```

If two branches change the schema, never merge the generated files by hand: resolve the migrations, then regenerate.

The schema lives in the Flyway migrations (`backend/src/main/resources/db/migration/V<n>__*.sql`). Nothing alters the schema at runtime.

**Until the first release the existing migrations are edited in place.** The project owner decided this on 2026-10-19: the service runs nowhere but in the tests and in GitHub Actions, so no database outside them exists, and every database there is built from the migrations from scratch. A change goes into the file that defines the object it concerns (the baseline `V1__initial_schema.sql` owns most tables, with their first triggers; a later file only for a trigger or a table of its own), and **no `V<n>` file is added for it**. It was done on 2026-10-08 (the former `V2` defaults were folded into `V1`, a report's date became a real `DATE`, `weather` became nullable, and the foreign keys from the diary's records to their project, report and author became `ON DELETE RESTRICT`: those to the user who signed are `ON DELETE SET NULL`, `project_members` still cascades; signed rows are protected by the triggers of V5 and V11) and on 2026-10-19 (hash version 2 of the audit log, backlog C3: four columns and a CHECK constraint on `audit_log` in `V1`; the triggers of V1, V2 and V12 are table level and did not change). **From the first `v*` tag every schema change is a new migration** (`V<n>`, the next number), because **the rule "a released migration never changes" starts with the first `v*` tag, and CI enforces it from then on** (job `immutable-migrations`, `scripts/ci/check-immutable-migrations.sh`): Flyway keeps a checksum of every migration it ran, so an edited one stops every database that already ran it. The script finds the newest `v*` tag reachable from `HEAD` and compares `backend/src/main/resources/db/migration/` with the tree at that tag: an added file passes, a file that was modified, renamed or deleted since the tag fails the job and is named. Until a `v*` tag exists the script says so and passes; in a shallow clone it fails instead of passing (the job checks out with `fetch-depth: 0`), and so does a tag at which that directory holds no migration (the directory moved: update the script). `db/grants/app-role.sql` is not guarded: it is not a versioned migration, and `migrate` applies it again at every release. The script has its own test (`check-immutable-migrations.test.sh`, throwaway git repositories), which runs in the same job. A mistake in a released migration is corrected by a new migration, never by editing the old one.

After pulling a change that edited an existing migration (most often `V1`), a local database that already applied the old one fails Flyway's validation (its checksum changed). Recreate it (the data is test data):

```bash
docker compose down -v && docker compose up -d   # then start the backend again
```

## Sessions

Login creates a server-side session (table `sessions`, valid for 12 hours) and sets an HttpOnly cookie with a JWT that only _names_ the session and the user. Every request looks the session up and loads the user's current role and flags from the database. So:

- logging out, deactivating or deleting a user, or changing a user's role or admin flag ends their sessions at once (the user has to log in again);
- rights claimed inside a token are ignored, and a token whose session is revoked, expired or unknown is refused with `401`, even with a valid signature;
- the application always keeps at least one active administrator: demoting, deactivating or deleting the last one answers `409`.
- **In the SPA** every call to the API goes through `apiFetch` (`lib/api.ts`). A `401` does not throw the person to the login page, because that loses what they typed: it raises a window event, and `SessionExpiredDialog` (mounted in `AppLayout`) offers to sign in again in place. The page underneath is untouched, so a half-written entry stays in its form and the person repeats the action (saving, signing). A page that has unsaved work says so (`setUnsavedWork`); a page that merely failed to load (a refused `GET`, nothing typed) is reloaded after signing in. The dialog signs in the **same account only** (the name is fixed), so the page never continues under another person; if the new session needs a password change it goes to that form. Covered by `e2e/session-expiry.spec.ts`.

## Passwords and login limits

- **Policy** (`PasswordPolicy`): 12 to 256 characters with a lower-case letter, an upper-case letter, a digit and a special character; **not a common password** (the letters of the password, lower-cased and without diacritics, are not one of a short list of base words such as `heslo`, `qwertz`, `admin` or `stavebni`, whatever digits and symbols surround them: `Heslo123456!` and `P@ssw0rd!2024` are refused, `Heslo-Je-Dlouhe-A-Neobvykle-7!` is not); and **does not contain the account's own login name** (case-insensitive, names under 3 characters are not looked for). The change-password form shows the same checklist (`frontend/src/lib/passwordPolicy.ts`, whose word list has to be kept in step with the server's); the server enforces it. The offline list is a first line only; the breached-password check below covers the long tail but fails open.
- **Temporary passwords:** an account made by an administrator, and an account whose password an administrator reset, has `mustChangePwd`. Such a session may only call `POST /api/auth/change-password`; everything else answers `403` with `code: PASSWORD_CHANGE_REQUIRED` (the SPA then shows the change form). This is decided from the database on every request, so whoever handed out the password cannot go on acting as that user. **A generated password expires after 7 days** (`users.passwordExpiresAt`, set by account creation, administrator reset and both command-line commands, cleared when the user chooses a password): a correct but expired password is refused at login with `401` and `code: PASSWORD_EXPIRED` (only someone who knows the password sees it), no session is opened, and an administrator issues a new one. A wrong password gets the ordinary answer, expired or not.
- **Change:** needs the current password; wrong answers are limited to 5 per 15 minutes per user; all the user's other sessions end. **Reset** (administrators, `Action.UserPasswordReset`): new generated password shown once (`Cache-Control: no-store`), every session of the user ends, a login lockout of the account is lifted. Neither password nor hash is written to the audit log.
- **Login limits** (table `rate_limit_attempts`, failures only): 30 failures per client address and 20 per account name within 15 minutes, then `429` with `Retry-After`. An attempt is **reserved before the password is checked** (under a database lock per key) and **given back only when it succeeds**, so any number of requests that arrive at the same moment cannot all slip under the limit, a refused request is not recorded (asking again does not extend the wait), and a success removes only its own attempt, not the failures of others. A client on IPv6 is counted as its **/64 prefix** (an IPv4-mapped address as the IPv4 address): rotating the last 64 bits gains nothing. The address comes from `CLIENT_IP_HEADER` when it is configured, otherwise from the TCP peer; `X-Forwarded-For` and the request body are never trusted. A known name can therefore be locked for up to 15 minutes by someone else; an administrator reset lifts it.
- **Breached passwords:** a new password is checked against the Pwned Passwords range API (`BreachedPasswordService`) and refused when it appears in a known breach. Only the first five hex characters of its SHA-1 leave the server (k-anonymity, with padding); the password is never sent. It fails open: if the service is unreachable, slow (2 s limit) or answers nonsense, the password is accepted and a warning is logged. Passwords generated by the application are not checked.
- `users.passwordChangedAt` records when the user last _chose_ a password; a temporary password (new account, administrator or command-line reset) clears it.
- **A login cannot outlive a reset.** The password is checked outside a transaction, so a reset (which ends all sessions) could land before the session is inserted. The session is therefore opened in a transaction that locks the user row and compares the stored password hash with the one that was checked: if it changed, no session is opened and the answer is the ordinary `401`. Changing one's own password does the same: it is refused with `409` when the password was reset or changed after it was checked, instead of overwriting the newer one. A request that was already running when a reset happened still finishes (the session is looked up once per request); that window is milliseconds and the reset ends everything after it.
- Unknown, deactivated and deleted accounts take the same time as a wrong password and get the same answer. Argon2 runs off the request threads, at most 4 at a time.

## Request and upload limits

- Every request body is capped before it is read: **256 KiB** for JSON, **6 MiB** for `POST /api/photos/upload`. Larger requests are answered with `413`.
- An upload carries **one** image of at most **5 MiB**, at most 8 multipart parts, and text fields of at most 256 characters (`400` otherwise). Ktor's `formFieldLimit` applies to every part including the file, so it is set to the request cap and the exact limits are checked in `PhotoRoutes`.
- The image type is checked by its magic bytes. Its dimensions are read from the **header** and checked **before** any pixel is decoded, so a tiny file that claims billions of pixels cannot exhaust memory: a **JPEG may claim up to 64 megapixels** (a phone photo is 12 to 50), other formats up to 16 megapixels (the JDK decodes them in full), at most 16,000 px per side; more is a `400`. A big JPEG is decoded **already reduced** (the reader skips pixels while decoding), so about 4 megapixels at most are held in memory whatever the size of the original. That holds for baseline JPEGs; for a **progressive** JPEG the decoder keeps coefficients for the whole image, so a 64-megapixel progressive file may need several hundred MB of native memory (not measured; see Follow-ups). A damaged image is a `400`. (JDK limits: WebP files pass the magic-byte check but the JDK has no WebP reader, so they end as a `400`; HEIC is not supported.)
- Accepted images are decoded once and stored as new metadata-free JPEGs (fitted into 1920x1080, never scaled up) plus a 400x300 thumbnail. **The camera's orientation (EXIF) is applied before the metadata is thrown away**, so a portrait photo is not stored on its side; a damaged EXIF block never rejects a photo. The stored width and height are those of the file on disk. Image work runs off the request threads, **two images at a time**; the engine drops a connection that sends nothing for 60 seconds (`requestReadTimeoutSeconds`), and the file is read on the IO dispatcher, not on a request thread.
- A photo belongs to **the entry the request names**: `reportId` is required (no "newest entry of the project" guess), and a bare date needs `projectId` (dates repeat across projects). The form offers photo upload only for a saved, unsigned entry. Errors never repeat what the database or a library said. A stored photo is served with `Cache-Control: private, no-cache`, so a logout or a lost membership takes effect.
- **Text of users and authorised persons** is bounded too, after trimming (characters are counted as a person counts them, an emoji is one): display name 200 characters, ČKAIT number 50; authorised person: name 200, organisation 200, scope of the authorisation or function 500. One character more, or a NUL character, is `400` with a Czech message (`... může mít nejvýše 200 znaků`) and changes nothing; a blank optional field is stored as nothing. The first administrator made from the command line follows the display-name limit. The database columns are unbounded `text`, so these limits are the only bound besides the 256 KiB body.
- The database stores **relative keys** (`photos/<uuid>_orig.jpg`, `photos/<uuid>_thumb.jpg`), never absolute paths, and the API never returns a path. A key is only followed when it has exactly that shape and resolves inside `UPLOADS_DIR`; otherwise the photo answers `404`. If the database write fails, the two files already written are removed.

## API overview (all under `/api`, JWT cookie auth unless noted)

- `GET /health` (public)
- Auth: `POST /auth/login`, `POST /auth/logout`, `POST /auth/change-password`
- Users (admin): `GET/POST /users`, `PATCH/DELETE /users/{id}`, `POST /users/{id}/activate|deactivate`, `POST /users/{id}/reset-password`; `GET /users/options` (project managers)
- Projects: `GET/POST /projects`, `GET /projects/{id}`, `PUT /projects/{id}` (the identification of the diary; the project's manager only; see "What an entry says"), `PUT /projects/{id}/site-manager` (replaces the site manager: see "Members" below)
  - Members: `GET/POST /projects/{id}/members`, `DELETE /projects/{id}/members/{userId}`
  - Authorized persons: `GET/POST /projects/{id}/authorized-persons`, `POST /authorized-persons/{id}/revoke`
  - Site handovers: `GET/POST /projects/{id}/handovers`, `GET/PUT/DELETE /handovers/{id}`, `POST /handovers/{id}/sign`
  - Reports: `GET/POST /projects/{id}/reports`, `GET/POST /projects/{id}/reports/{idOrDate}`, `POST …/sign`, `POST …/acknowledge`, `GET /reports/{id}/pdf`, `GET /projects/{id}/reports/{idOrDate}/pdf`
    - `GET /projects/{id}/reports` is a **page**: `?limit=` (1 to 1000, default 400) and `?offset=`, newest day first, with the project's total in the `X-Total-Count` header; the body is still a plain list. Anything else is `400`. The photos of a page are loaded in one query (the list asks the database a fixed number of questions however many entries there are). The SPA loads older pages on request.
    - `POST /projects/{id}/reports` only creates (201, or 409 when the day has an entry); `POST …/reports/{date}` saves: it creates the entry or changes only the fields the request mentions. A bad or missing body is a 4xx and changes nothing. Besides the day's work an entry carries the **fields of the vyhláška** in `details` (a JSON object of text by key: `materials`, `machinery`, `testsAndChecks`, `safetyNotes`, `dustMeasures`, `accessibilityMeasures`, `defects`, `otherNotes`; a key that is left out keeps its text, an empty text clears it, an unknown key or a text over 5 000 characters is `400`) and, per trade in `workersByTrade`, an optional `names` list (no more names than workers). See "What an entry says".
    - **Two people editing one entry:** every entry carries `updatedAt`. A save that sends it back as `expectedUpdatedAt` is a compare-and-set on the locked row: if somebody else saved in between it is refused with `409` and `code: STALE_VERSION` (the SPA then offers to load the other version) and nothing is overwritten. A save without it is last-one-wins. The SPA always sends it for an existing entry, and for a day that looked empty when the form loaded it sends `expectNew: true`: if somebody created the entry in the meantime, the save is refused with the same `STALE_VERSION` instead of replacing it. `POST …/sign` accepts the same `expectedUpdatedAt` in its body: a signature covers a version, and a signer who names the one they saw is refused (`STALE_VERSION`) when the stored one is different. The form only offers "Podepsat a uzamknout" for a saved entry without unsaved changes (so a signature never covers words that were not saved), and is read-only once the entry is signed.
    - **The form never loses or doubles a save:** it shows "Načítám záznam…" until the entry (or the answer that the day has none) and the person's role in the project have arrived, so nothing typed before can be overwritten by the loaded entry; an entry that could not be loaded stays locked and cannot be saved. Only the project's BOSS and WORKER members get an editable form (the others, INSPECTOR and INVESTOR, would get `403`, see Rbac `ReportCreate`): they see it read-only with a note. One save runs at a time: the button is disabled and says "Ukládám…" until the answer comes, so a double tap sends one request (a second `expectNew: true` would otherwise be refused as a false `STALE_VERSION`). The button says "Uložit záznam" for a day without an entry and "Uložit změny" for an existing one; after a save "Uloženo HH:MM" shows until the next change, which shows "Neuložené změny" instead. While there are unsaved changes, closing or reloading the tab asks first (`beforeunload`). Leaving through a link inside the application or logging out does not ask yet, and nothing is kept as a draft (backlog B2 in [`docs/REVIEW-AND-PLAN.md`](docs/REVIEW-AND-PLAN.md)).
    - **Workers:** an entry holds a list of `{trade, count, names?}`, at most 50 trades, each with a name and a whole head count from 0 to 100,000, and an optional list of the **names** of the people (at most as many as the head count, at most 200 per trade, each at most 100 characters, no NUL character); the form takes the names separated by **semicolons** because a name often has a comma in it ("Ing. Jan Novák, Ph.D."), and the PDF prints them the same way. Nothing is defaulted (a trade without a count used to become 1, which invented data in a legal record) and a malformed list is a `400`; the form has one row per trade.
- Photos: `POST /photos/upload`, `GET /photos/{id}`, `GET /photos/{id}/thumb`
- Audit log (admin): `GET /audit?limit=200`

### Roles: what a person may do follows their role in the project

A person has **two kinds of role**, and they do different things:

- the **role in a project** (`project_members.role`: BOSS = stavbyvedoucí / project manager, WORKER, INSPECTOR, INVESTOR) decides **everything they may do inside that project**: the same person can be the manager of one project and an ordinary worker in another. It is passed to every permission decision (`Resource.role`) and read from the database inside the transaction, so a changed role applies to the very next request. The API shows it as `myRole` on a project (null for an administrator who is not a member), and the SPA offers actions by it;
- the **global role** of the account (`users.role`) is the role a person usually has: it is the default offered when adding them to a project, and it decides **who may create a project** (global BOSS, because the creator becomes the project's manager). It gives no right inside a project.
- the **administrator flag** is independent of both: it opens user administration and the audit log, lets the person read every project, and is the audited way in (below). It gives no write right in a project.

What each project role may do (the matrix is pinned by `RbacTest`):

|                                                               | BOSS                                   | WORKER | INSPECTOR | INVESTOR |
| ------------------------------------------------------------- | -------------------------------------- | ------ | --------- | -------- |
| write a report / add a photo                                  | yes                                    | yes    | no        | no       |
| correct a report                                              | any                                    | own    | no        | no       |
| sign a report (needs a ČKAIT number)                          | yes                                    | no     | no        | no       |
| delete a photo (permitted, but no route exists yet)           | yes                                    | no     | no        | no       |
| acknowledge a signed report                                   | no                                     | no     | yes       | yes      |
| sign a site handover protocol                                 | yes                                    | yes    | yes       | yes      |
| manage members and authorized persons                         | yes (and an administrator)             | no     | no        | no       |
| change the identification of the diary (`PUT /projects/{id}`) | yes (only the manager of THIS project) | no     | no        | no       |
| replace the site manager (`PUT /projects/{id}/site-manager`)  | yes (only the manager of THIS project) | no     | no        | no       |

**Members:**

- Only the project's manager, or an application administrator as the audited way in (decision D1), may add a member or change a role. Nobody changes their own role (an administrator who joined as a worker cannot promote themselves afterwards).
- The project's **site manager** (`projects.siteManagerId`) can be neither removed nor given another role, and a project always keeps a BOSS membership. That member can still be deactivated or deleted as a user, and the last-manager check counts such users too (see Follow-ups). The role of a membership has **no database default** (migration V7): a forgotten column must not make someone a manager who may sign the diary.
- **Replacing the site manager** (`PUT /projects/{id}/site-manager`, body `{siteManagerId, reason?, updatedAt}`):
  - Only the manager of the project may do this; the new one must be an active member whose role in the project is BOSS and who holds a ČKAIT number (decision D2), otherwise `409`.
  - The version (`updatedAt`) is required like for any change of the project (`400` without it, `409 STALE_VERSION` when the project changed meanwhile).
  - The previous site manager stays a manager of the project, and from then on only the NEW site manager is protected against removal and demotion.
  - The audit row `project.site_manager.change` keeps who it was and who it is, with their ČKAIT numbers, and the reason. The entry PDF names the site manager in the identification.
- **Project membership and administrators:**
  - Project-scoped endpoints require project membership. App admins can **read** every project, but being an admin gives no right to write: creating, overwriting, signing or acknowledging a report, uploading or removing a photo, and creating, changing, deleting or signing a site handover protocol all require real membership of that project. The membership is judged inside the transaction, on rows locked `FOR UPDATE`, never assumed.
  - **Joining a project as an administrator is the audited way in** (decision D1): a project manager of the project, or an administrator, may add members (an administrator adds themselves), and the audit row names the project, the user and the role before and after.
  - An administrator cannot change their own role (they could otherwise make themselves a project manager and then a member of any project); changing someone's role or administrator flag ends their sessions and is audited with before and after, and fixing a display name does not log anyone out.

**Signed records are immutable in the database too** (migration V5, triggers that compare the whole row): a signed daily report cannot be changed or deleted (only the acknowledgement can still be added), photos cannot be added to, changed on or removed from a signed report, and a signed handover protocol cannot be changed or deleted. The application checks all of this first; a photo whose processing was still running when the report was signed is refused at insert time, not given to the signed record. The audit rows of photos, handovers, authorised persons and members carry the entity id and before/after snapshots (the `photo.upload` row holds the SHA-256 of both stored files; `PhotoService.deletePhoto`, which no route calls yet, would record them as null).

### Daily reports: signing and acknowledging

- **Signing (`POST /projects/{id}/reports/{idOrDate}/sign` and `POST /reports/{reportId}/sign`):**
  - Body: `{"password": "…", "expectedUpdatedAt": "…"}`.
  - **Qualification (decision D2):** Only a member whose role **in that project** is BOSS may sign (a global BOSS who is only a worker here may not), **and who holds a ČKAIT number**: without one the answer is `403` with `code: SIGNER_NOT_QUALIFIED` and a message that says why. The same number is required to be made a manager of a project (adding a member as BOSS, naming a site manager, creating a project) so that nobody is given a role they cannot use. One gap: `createProject` checks the number of the site manager it names, but adds that person with their **global** role instead of BOSS (see Follow-ups).
  - **Password re-entry (decision D8):** Signing asks for the password again so a session that was left open or stolen cannot sign. The routes first decide whether the person may sign this entry at all (a worker is told `403` without being asked for a password), then check the password (`400` "Heslo není správné", never `401`, which would look like a lapsed session; at most 5 wrong answers per 15 minutes per person, then `429`; a right password gives its attempt back, like a login), then sign in one transaction.
  - **Signed once & numbered at signing (decision D11):** A report is signed **exactly once**: a second request answers `409` and changes nothing (signer and time stay). The number of the entry in the diary is given at that moment: the Nth signed entry of a project is number N, so the signed entries follow one another without gaps however many drafts were started and abandoned; a draft has no number (`sequenceNumber` is `null` in the API, empty in the CSV of `CsvExportService`, which has no route, `"zatím bez čísla"` on a draft PDF). The number is assigned under the audit lock, is part of what the signature covers, and is checked by a database trigger (V13: the number given at signing must be the next one of the project; a signed entry must have one; a draft cannot be given one). Entries signed before V13 keep the number they were signed with. Numbers follow the order of signing, not the order of the days. A non-member gets `403`.
- **What a signature covers:**
  - In the statement that locks the entry the server stores `daily_reports.signatureHash`: the SHA-256 of the canonical JSON (sorted keys) of the entry as it is stored: id, project, date, number, author, work description, workers list, control-day flag, construction object, weather, late-entry flag and reason, the **fields of the vyhláška** (see "What an entry says") and the **names** in the workers list, **who signed and when**, and the **SHA-256 of every photo file** (recorded at upload in `photos.sha256` and `photos.thumbSha256`).
  - **Signature format (`daily_reports.signatureFormat`, V14):** `1` for what was signed before the vyhláška detail fields existed and `2` for an entry signed since; the server sets it at the moment of signing, before the hash is made, and checks an entry in the format it was signed in. Each format is frozen (`GoldenSignatureTest` pins the exact content and hash of both; a field added later needs a format 3, never a change to format 2). From format 2 on a missing hash is a failure, not "nothing to compare". The signed-records triggers (V5) freeze the column and the format afterwards.
  - **Verification (`GET /reports/{id}/signature`, members and administrators):** Hashes the entry again and answers who signed (with the signer's **current** name and ČKAIT number: the signature covers the signer's id, and neither the name nor the number is stored at signing, so a later edit of the user changes what the check and the PDF show; see Follow-ups), whether `contentMatches`, and whether the photo files on disk still hash to what was recorded (`photoFilesMatch`): a change made to a row or a file **behind the application's back**, which the audit log alone would only show if the whole chain were rewritten as well, is found. The entry page offers "Ověřit podpis"; the PDF has a signature block with the signer, the time (Prague time), the hash and the hash of the audit row that recorded the signature. Entries signed before the hash existed (test data only) have none and say so.
  - This is a **content hash bound to a password re-entry, not a qualified electronic signature**: that is a separate decision (needs the lawyer's sign-off, see the Release gate).
- **Addenda (`GET/POST /reports/{id}/addenda`):**
  - How a **signed** entry is corrected or completed: a signed entry cannot be changed, so a mistake or a missing remark stands next to it as a new record with its author and time.
  - Members whose role in the project is BOSS or WORKER may add one (an inspector, an investor, an administrator who is not a member and a stranger may not; they may read); the text is 1 to 4000 characters; an entry that is still being written takes none (it is edited directly, `409`).
  - The table is **append-only in the database** (migration V9: no update, no delete, and an insert only for a signed entry), each addendum is audited (`report.addendum.add`, the whole text in the audit row) and appears in the PDF under "Dodatky". An addendum is not part of what the signature covers (it comes after it).
- **Entries of other parties (`GET/POST /reports/{id}/remarks`; technical supervision, author's supervision, client, authorities):**
  - Made **also after the day's entry was signed** and never changed or deleted (append-only in the database, migration V10, which also adds `remarks.externalAuthor` and the type `EXTERNAL_ENTRY`).
  - A member whose role in the project is INSPECTOR or INVESTOR writes in their own name; an authority or a person without an account does not write at all: **the project's manager (BOSS) records the entry for them and has to name them** (decision D9; the entry shows "Name of the party (zapsal manager)", and is marked official).
  - A manager cannot add an entry without naming a party (the manager's own words belong in the daily entry); an inspector or investor cannot write for somebody else; a worker, an administrator who is not a member and a stranger cannot write (403); members and administrators may read. 1 to 4000 characters, the party's name up to 200.
  - Each entry is audited (`report.remark.add`, the whole text and who spoke for whom) and appears in the PDF under "Zápisy dalších osob". It is not part of what the signature covers, and it does not change it.
  - **Not done yet:** attaching the scanned or digitally signed protocol of an authority (a non-image file upload airlock).
- **Acknowledgements (`POST …/acknowledge`):**
  - Records that **a party** has taken note of the entry: **every** member whose role in the project is INSPECTOR or INVESTOR (the technical supervision, the author's supervision, the client) does so on their own behalf and **once** (a second try by the same person is `409`, the first record stays), and each is on record in the table `report_acknowledgements` (migration V11: append-only, insert only for a signed entry, one row per person and entry; it replaces the single acknowledgement of the old scheme, whose two columns were dropped and moved over).
  - It only works on a **signed** report (otherwise `409`). The entry lists all acknowledgements (`acknowledgements`, oldest first, with name, role and time; `isAcknowledged` is true when there is any), the PDF has a "Seznámení se záznamem" section, and each one is audited (`report.acknowledge`). `DashboardService` would count signed entries that nobody has taken note of, but it has no route. Since V11 **a signed daily report cannot change in any column at all** (the old exception for the acknowledgement is gone).
- `GET/POST /reports/{reportId}/…` take a report id only; a bare date is `400` (a date is only unique within a project, so use the project-scoped route). A report id of another project is `404` through `/projects/{id}/reports/{reportId}`.
- Every report change is written to the audit log in the same transaction, with the real report id and a before/after snapshot (`report.create`, `report.update`, `report.lock`, `report.acknowledge`).

## Entry dates and late entries

A new daily entry is **on time** for today and for any day since the previous working day (Monday to Friday; public holidays are not considered): on a Monday that is Friday, Saturday, Sunday and Monday. An entry for an **earlier** day is a **late entry**: it needs a reason (at most 1,000 characters), is flagged (`isLateEntry`, `lateEntryReason`) and the flag and reason are part of the record, the audit snapshot and the PDF (`Pozdní zápis:`). An entry for a day in the **future** is refused. "Today" is the date in Prague (decision D10). Only a _new_ entry is checked: correcting an existing one is not a new entry, and the reason of a late entry stays. A flagged entry without a reason cannot exist in the database either (check constraint, migration V3). The form asks for the reason when it opens a day before the previous working day, and does not offer a date in the future.

**This is not the rule of příloha 12 (part C, point 2)**, which asks for an entry on the day, at the latest on the next day on which work is done on the site (up to one working week for technically simple buildings, with the building authority's consent). The two differ: work on a Saturday makes an entry for Friday that is written on Sunday or Monday late under the decree, but not here; after a stoppage the decree allows the last day to be entered when work resumes, while the app flags it; public holidays are ignored; and only the creation of an entry is checked, so a draft created on time and signed days later is never flagged. Which rule to apply, and whether to check at signing, is a question for the lawyer (Release gate).

## Weather

The weather of a day is **entered by hand** (decision D12): a free-text condition (the form suggests common ones), the lowest and the highest temperature. Everything is optional; an entry with no value is stored as no weather, and sending an empty `weather` object on a save clears it, while leaving `weather` out keeps what is stored. Temperatures must lie between -60 and 60 °C and the lowest cannot exceed the highest; the text is at most 200 characters. The PDF shows it as readable text (`zataženo, 8,5 až 15 °C`, or `Neuvedeno`), and the audit snapshot keeps that same text, because snapshots hold no decimals (a number's textual form could change on the way through `jsonb` and break the hash chain). **Not done:** filling the weather in automatically from Open-Meteo; its free API is non-commercial, so that needs a commercial key first. `WeatherService` still exists for that purpose but nothing calls it.

**Part A (the identification of the diary):**

- The form is the same for both (`ProjectFields`), a save **must** carry the version it loaded (`updatedAt`; without it `400`) and is refused with `409` when somebody else changed the project meanwhile, a save that changes nothing writes nothing (no new version, no audit row), and the audit row `project.create` names the project and keeps what was entered (`project.update` keeps the project as it was and as it is). The site manager is not changed by an edit.
- The entry PDF prints the project **as it stands when the PDF is made**, not as it stood when the entry was signed: a signed entry does not carry a copy of the identification and the signature does not cover it. Never rename a key: it is part of the signed content.

## Cross-site requests

The session cookie is `SameSite=Lax`. In addition, `CrossSiteRequestGuard` refuses every state-changing request (anything but GET, HEAD, OPTIONS) under `/api/` that a browser makes on behalf of another site, with `403`:

1. an `Origin` listed in `CORS_ALLOWED_ORIGINS` is accepted;
2. otherwise `Sec-Fetch-Site` decides: `same-origin` and `none` pass, `same-site` and `cross-site` are refused;
3. browsers without that header send `Origin` on every POST: its host has to equal the `Host` the request was sent to;
4. with neither header (scripts, curl, tests) the request passes: only a browser can be tricked into a cross-site request.

Behind the Vite dev proxy the page and the API are the same origin for the browser (`Sec-Fetch-Site: same-origin`), so nothing needs configuring.

## Security headers

`configureSecurityHeaders` (`Application.kt`) sets the same headers on every response of the Ktor server: API answers, errors (`401`, `403`, `404`, `413`), CORS preflights and the files of the SPA. `SecurityHeadersTest` checks each of those kinds. `e2e/security-headers.spec.ts` reads the headers from whatever `BASE_URL` serves: the Vite dev server, which sets a development version of them in `frontend/vite.config.ts` (its `script-src` allows inline scripts for hot reloading), or the built image in the `e2e-image` job. A change to a header therefore goes into those three places.

- `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self'; object-src 'none'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`. A page talks to its own origin and to nobody else: the weather is typed by hand (decision D12) and nothing calls Open-Meteo, so it is not listed.
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`.
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`: features the application does not use are off for the page and for anything it embeds. `camera=()` governs `getUserMedia` only; the photo field is a plain `<input type="file">`, which hands the choice to the operating system and still opens the camera app on a phone. A feature that used `getUserMedia` would have to change this header.
- `Cross-Origin-Opener-Policy: same-origin`: no other site's window shares the browsing context group of the application.
- `Cross-Origin-Resource-Policy: same-site`, **not** `same-origin`: `same-origin` would stop photos from loading on an SPA host listed in `CORS_ALLOWED_ORIGINS`.
- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`, in production only (plain HTTP development must not pin HTTPS).

## Database roles

The protections the migrations put into the database (the audit chain's triggers, the signed-records triggers, the append-only tables) are only as strong as the database role that the running application connects as. **A role that owns the tables can switch every one of those triggers off**, so anybody who stole the application's password could rewrite history and hide it. Therefore, in production, there are two roles (decision D5):

- the **owner** creates and changes the schema (`migrate`); its password is never on the application's machine;
- the **application's role** (`app`, created by `scripts/sql/bootstrap-app-role.sql`) owns nothing. `migrate` gives it, in `db/grants/app-role.sql`, data access to the tables (select, insert, update, delete; not truncate, not trigger) and read access to the schema history, and takes **update, delete and truncate on the audit log away**. It cannot create or drop a table, alter or disable a trigger, or change a role.

The application in production **does not migrate** (`MIGRATE_ON_START` defaults to false there): on a schema that is not current it refuses to start with "the database schema is out of date ... run the migrate command". The `create-admin` / `reset-password` commands follow the same rule in production. In development and in the tests one role does everything, as before.

```bash
# once per database, as a superuser (creates the role "app"):
psql -v ON_ERROR_STOP=1 -v app_password="$APP_DB_PASSWORD" -d stavebni_denik -f scripts/sql/bootstrap-app-role.sql
# at every release, with the OWNER's credentials, from CI or the operator's machine (not from the application's machine):
DB_MIGRATE_USER=<owner> DB_MIGRATE_PASSWORD=<...> DB_APP_ROLE=app JDBC_URL=<...> \
  java -cp backend-all.jar cz.stavebni.denik.cli.AdminCliKt migrate
```

`DatabaseRolesTest` runs the facts: under the application's role (a) normal work succeeds, (b) about twenty statements that would weaken the protections are refused (create, drop or alter a table, disable or drop a trigger or function, truncate, delete or update the audit log, change the schema history, alter or create a role), (c) the whole application flow (the service path: project, entry, signature, audit chain) works and the chain verifies, and (d) a table that a later migration adds is covered with the same limits. The CI Docker job does it for real: it creates the role, shows that an unmigrated schema stops the application, migrates as the owner, boots the image as the application's role, and checks that this role cannot create a table, disable a trigger, truncate or delete the audit log. **The simple one-role setup still works** (`MIGRATE_ON_START=true`, `DB_USER` = the owner), but then the application's role owns the tables and none of the above holds: use it for staging with test data only. Backups and the restore drill are in "Backups and the restore drill".

## Backups and the restore drill

The evidence is the database (including `audit_log`) **and** the photo files; the database holds a SHA-256 of each photo, so a database restored without its photos is detectably incomplete. `scripts/backup/` holds three scripts, all of them exercised in CI:

- `backup.sh` writes `denik-<UTC time>/`: `db.dump` (`pg_dump` custom format, one consistent snapshot, no owners or grants: whoever restores becomes the owner), `photos.tar.gz` (taken **after** the dump, so a photo that arrived in between is a harmless orphan file and never a database row without its file), `manifest.json` (schema version, number of photo files, **the newest audit-log row before the dump**) and `SHA256SUMS`. It prints that audit head: it is the anchor for the restored database (an anchor stays valid while the log grows) and belongs somewhere the database owner cannot reach (see "Audit log").
- `restore.sh` restores into an **empty** database and an empty uploads directory and refuses anything else, so a restore can never overwrite live data (to replace a damaged database, restore into a fresh one and switch over). It checks the backup's checksums, runs `pg_restore --exit-on-error`, (with `APP_JAR`) **migrates the restored copy to the schema of that jar** first, so a backup made by an older version can be verified by newer code (a backup of a newer schema cannot be migrated and fails there), checks **every photo file against the hash recorded at upload**, and, given `APP_JAR`, runs `audit-verify <anchor>` (the chain verifies and still contains the row the manifest recorded) and `verify-signatures` against the restored database. A backup of a chain with audit rows of both hash versions restores and verifies, anchors included (`AuditBackupRestoreTest`; see "Audit log"). It prints "restore drill passed" only when all of that holds.
- `drill.sh` does backup and restore and then shows that the restore **refuses** a non-empty target database, a damaged backup file, and a photo that was replaced even though the backup's own checksums were regenerated to match. A restore that cannot fail proves nothing.

`verify-signatures` (an operator command that only reads, like `audit-verify`) hashes every signed entry again from the database (text, signer, time, photos) and every photo file under `UPLOADS_DIR`, and compares them with what was recorded when the entry was signed and the photo uploaded; exit `1` names each entry that no longer matches. Entries signed before hashes existed are counted, not failed. It is also what proves, after a restore, that **what was signed is as it was signed**.

CI runs `drill.sh` after the end-to-end tests, on the database and photos those tests left behind (real signed entries, addenda, remarks, acknowledgements, photos), so the drill is a check on every change, not a promise. **Not done, because it needs infrastructure that does not exist yet:** running `backup.sh` on a schedule, and copying the result to encrypted storage that the application's machine cannot delete from (the backup holds personal data and the evidence itself); and a periodic restore drill against production data. `PG_DOCKER_IMAGE` lets the scripts run `pg_dump`/`psql` from a container when the local client is older than the server (`pg_dump` refuses a newer server).

## Audit log

Every change goes through `AuditService`: the audit row and the business change share one transaction, appenders are serialised by an advisory lock, and each row carries the hash of the previous one (a chain). The database refuses `UPDATE`, `DELETE` (migration V1) and `TRUNCATE` (V2) on `audit_log` with triggers. Those triggers stop mistakes and an application that holds ordinary privileges; **whoever owns the table can still switch them off**, and a log that was cut short, or emptied, is still a valid chain. So the newest row has to be **recorded outside the database**, and checked against:

```bash
fly ssh console -C "java -cp /app/app.jar cz.stavebni.denik.cli.AdminCliKt audit-head"          # prints <id>:<hash>; store it somewhere the database owner cannot reach
fly ssh console -C "java -cp /app/app.jar cz.stavebni.denik.cli.AdminCliKt audit-verify 1234:ab12…"   # chain + that row 1234 still exists unchanged
```

- **Rows of users:**
  - Every change of a user (`user.create`, `user.update`, `user.activate`, `user.deactivate`, `user.delete`, `user.password_change`, `user.password_reset`, and the operator commands `user.bootstrap_admin` and `user.password_reset`) is written by `AuditService.auditedWrite`, after the change and in the same transaction: a change that fails leaves no row, and a row that cannot be written leaves no change. It is the only way an audit row is written (the legacy `auditedTransaction`, which wrote the row first, with `before = after = null` and the nickname as `entityId`, is gone).
  - `entityId` is the user's id. `before` and `after` are a `UserSnapshot` (`UserSnapshot.kt`): id, nickname, display name, role, administrator flag, active, `deletedAt`, ČKAIT number, `mustChangePwd`, `passwordChangedAt` and `passwordExpiresAt`. A creation has no `before`; a command-line action has no acting user. So `user.create` records the role, the administrator flag and the ČKAIT number the account started with.
  - **Never a password, a hash or a token:** the state of the password is only those flags and times (a temporary password has an expiry and no "chosen" time, a chosen one the opposite). `UserAuditRowsTest` checks the field names of the snapshot and searches every stored row for the passwords and hashes the operations produced.
- **Row format: hash versions 1 and 2 (backlog C3):**
  - **One chain, two formats** (`audit_log.hash_version`). Version 1 (the format until hash version 2; the application no longer writes it, tests build such rows by hand, and no production row exists) hashed the whole row, with the `before` and `after` snapshots as `jsonb` gives them back; it is frozen and pinned by a golden vector (`AuditHashTest`). **Every new row is version 2.** `verifyChain` applies the rule of each row's own version, and a row's `prev_hash` is the hash of the row before it whatever that row's version is. A row is never hashed again (no migration touches a hash), so every anchor ever recorded stays valid; a version 3 would be for new rows only. An anchor, `audit-head`, `audit-verify`, `GET /api/audit/verify`, the anchor script and the manifest of a backup only handle `<id>:<row_hash>`: none of them changes.
  - **Version 2 is two hashes** (the exact bytes are in `AuditHash.kt` and pinned by golden vectors that an independent implementation produced, so a verifier in another language can be written from this text):
    1. `payload_text` is **the text of everything the row says**: a compact JSON object with the keys `action`, `actorId`, `after`, `before`, `entityId`, `entityType` and `ts` (UTC, milliseconds), keys sorted, numbers as the snapshot had them. It is stored as that text and **hashed as it is stored**, so verification never depends on a JSON library or on `jsonb`, which rewrites numbers (`1e-7` becomes `0.0000001`; backlog M10). `payload_digest = SHA-256( lp("stavebni-denik/audit-payload") ‖ lp(salt) ‖ lp(payload_text, UTF-8) )`, where the salt is 32 random bytes (`payload_salt`, 64 lower-case hex characters), **new for every row**.
    2. `row_hash = SHA-256( lp("stavebni-denik/audit-row") ‖ lp("2") ‖ lp(prev_hash) ‖ lp(project_id, or nothing for a row of no project) ‖ lp(payload_digest) )`.
    - `lp(x)` is the length of `x` as four bytes, big-endian, followed by `x`; `prev_hash` and `payload_digest` are 64 lower-case hex characters, `project_id` a lower-case UUID. With the lengths in front, no two different sets of fields give the same bytes.
  - **What is stored** (the table is defined in `V1`): `hash_version`, `project_id` (nullable; no foreign key, because the evidence outlives anything), `payload_text` and `payload_salt`, next to the old columns. `ts`, `actor_id`, `action`, `entity_type` and `entity_id` still exist and repeat the payload so that it can be searched; `verifyChain` checks that each says what the payload says. **`before` and `after` are empty in a version 2 row** (read them with `payload_text::jsonb -> 'after'`), and so are the legacy `ip` and `user_agent` (decision D7). The CHECK constraint `audit_log_hash_version_shape` refuses any other shape and `verifyChain` reports one that got in anyway, so nothing readable sits in a row without being under its hash. Not covered: the row's `id` (the order is the chain's) and `audit_request_context` (D7). The append-only triggers (V1, V2) and the application role's grants are table level and cover the new columns unchanged.
  - **Which project a row belongs to** (`AuditProject`, worked out inside `AuditService.auditedWrite` from what the change already says, so that no caller can forget it; a row of a project that names none, and an entity type without a rule, are refused and roll the change back): `user.*` rows (also the operator commands) belong to none, because users are global; `project.*` rows (creation, identification, site manager, members) to the project itself; `report.*` (entry, signature, acknowledgements, addenda, entries of other parties), `photo.*`, `siteHandover.*` and `authorizedPerson.*` to the `projectId` of their snapshot. Verification does not apply this rule again: what was hashed is what counts.
  - **One project's part of the chain (for the § 166(3) export, backlog C5):** a row hash is a function of three things only: the previous hash, the project and the salted digest of the payload. So the rows of one project can be handed over in full (`payload_text` and `payload_salt`) and every other row as a **stub**: `id`, version, `prev_hash`, `project_id`, `payload_digest`, `row_hash`. The recipient recomputes every hash and every link and checks that no stub names the project of the export. A row of that project hidden as a stub fails, because its project id is inside the hash. **A stub does not say what its row says:** the digest is salted, and the salt is never in a stub, so a recipient cannot confirm a guess about a row of another project (an unsalted digest would let them test the guess). It does show that the row exists, where it sits and the id of the other project (a random identifier, no name); the time, actor, action and entity of the row are under the digest. `AuditChainVerificationTest` does exactly this with the export of one project out of three.
  - **Limits:** a cut tail is not seen by a slice (as for the chain itself, see the anchor above); a version 1 row cannot be a stub, because its hash needs the whole row (this only concerns test data); the exporter must never write the `payload_salt` of a row of another project into an export; the rows of users are stubs in every export.
- **Verification commands and API:**
  - `audit-verify` exits `0` when the chain is intact (and the anchor, if given, is found unchanged) and `1` when it is not, printing the reason; `3` means the check **could not run** (database unreachable, schema missing): that is neither "intact" nor "broken", and an unattended check must treat it as a failure.
  - All three verification commands (`audit-head`, `audit-verify`, and `verify-signatures`) only read: they **do not migrate** the schema, so a read-only database role is enough and a scheduler cannot change a database that another version of the application owns. Without an anchor the check cannot see a cut tail.
  - The same check is available to administrators as `GET /api/audit/verify` and `GET /api/audit/verify?anchor=<id>:<hash>`, which also returns the current `head`. An anchor stays valid while the log grows.
- **Nightly external anchor (decision D4, `.github/workflows/audit-anchor.yml` + `scripts/audit/record-anchor.sh`):**
  1. Checks that the newest record in a PRIVATE anchor repository still matches its RFC 3161 timestamp token.
  2. Verifies the whole chain against the head that record names (intact and not cut below it) and takes the new head **from that same run** (a second run could be shown a different log).
  3. Writes the new head as `anchors/anchor-<UTC time>.txt` (head, time, the previous record and its SHA-256) with the token request and the token from an independent time-stamping authority, verifies that token against the authority's certificate **pinned in the anchor repository** (`tsa/ca.pem`), and pushes it.
  - Nothing is recorded when any check fails (exit `1` chain or record not intact, `2` not configured, `3` could not complete), and the push is never forced, so it fails when the anchor repository moved during the run.
  - A history rewritten earlier is **not** detected by the push: the branch rule (no force-push, no deletion) and the time-stamped, hash-linked records are what protect it, and a record that was edited no longer matches its token. A token is verified as of the time it was issued, so a rotated authority certificate does not fail old records (add the new certificate to `tsa/ca.pem`).
  - **Limits to know:** what is written after the last record (up to a day, longer when a night fails) is not protected yet; the job cannot tell you that it stopped running (a failed night notifies, but GitHub also switches scheduled workflows off in a repository without activity for 60 days, silently): watch the age of the newest record with something outside this workflow.
  - **Testing & verification:** Tested in CI (`scripts/audit/anchor-test.sh`) against a real database and a real RFC 3161 exchange with a throwaway authority, including the refusals: an unreachable authority, an earlier record edited after it was time-stamped, a log that lacks the row an earlier record named, and a certificate that is not the pinned one. What a verifier does later: `openssl ts -verify -data anchors/anchor-….txt -in anchors/anchor-….tsr -CAfile tsa/ca.pem` proves the record existed at that time, and `audit-verify <head>` proves the database still contains that row unchanged.
  - **Still to do by a person:** create the private anchor repository and its branch rule, pin the authority's certificate, and set the secrets (`AUDIT_JDBC_URL`, `AUDIT_DB_USER`, `AUDIT_DB_PASSWORD`, `AUDIT_ANCHOR_TOKEN`) and variables (`AUDIT_ANCHOR_REPO`, optional `AUDIT_TSA_URL`) once a production database exists (`docs/DEPLOYMENT.md`). (Printing the entry's `report.lock` row in the PDF footer is code that is not written yet; backlog B8.) **The workflow fails while it is not configured**, so that nobody believes the log is watched when it is not (disable it until a production database exists). The database must be reachable from GitHub's runners; otherwise run the same script where the database is. Separate database roles for migrations and for the application (decision D5) are done (see "Database roles"); what is still to do is to use them in the real production database.

- **Address and user agent (decision D7):**
  - The IP address and user agent of a request are personal data, so they are **not part of the audit hash**: the chain is permanent and cannot be pruned. `AuditService` writes them, in the same transaction as the audit row, to `audit_request_context` (one row per audit row; they come from the `RequestContext` the server puts on every call, so a change made by an operator command has none; the user agent is cut to 256 characters).
  - Sign-ins, failed sign-ins and sign-outs go to `access_log`, which is **not** part of the legal chain: it is a record for security investigations. A failed attempt against a name that does not exist records no name at all, because what was typed into that field may be a password; against an existing account it records the account. Not recorded: a failed attempt that the rate limiter refused (it is already counted), and anything about reads.
  - **12-month retention:** Both tables are kept **twelve months**: the database refuses to change a row, or to delete one younger than that (migration V12; whoever owns the table can still switch the trigger off, as with the others), so that someone holding the application's credentials cannot erase their traces, and `AdminCliKt prune-access-records` deletes what is older. **Run it regularly** (`docs/DEPLOYMENT.md`): the period is a promise made in the privacy notice. Backups contain these tables too, so they follow the same period.
  - **Worker names in the permanent chain:** The audit snapshots of an entry contain what the entry contains, including the **names of the people on site** (the law asks for them in the diary), and the audit chain is permanent and cannot be pruned: those names cannot be erased from it. Their legal basis is the duty to keep the diary; it belongs in the GDPR paperwork (decision D13).

## First administrator and operator CLI (`AdminCliKt`)

A fresh database has no users, so nobody can log in. Operator commands run against the database from inside the application image (`cz.stavebni.denik.cli.AdminCliKt`). Except `migrate`, they connect as the application's role (`JDBC_URL`, `DB_USER`, `DB_PASSWORD`). **In production** no command but `migrate` changes the schema, and each of them refuses to run on a schema that is not current (exit `3`). Elsewhere `create-admin`, `reset-password` and `prune-access-records` migrate the schema first; the three read-only commands never do.

- `migrate`: runs the Flyway migrations as the schema owner (`DB_MIGRATE_USER`, `DB_MIGRATE_PASSWORD`, falling back to `DB_USER`/`DB_PASSWORD`) and applies `db/grants/app-role.sql` when `DB_APP_ROLE` is set; `1` when the database has migrations this build does not know.
- `create-admin <nickname> <displayName>`: creates the first administrator (refused once an active administrator exists).
- `reset-password <nickname>`: issues a new temporary password, ends all sessions of the user and lifts a login lockout.
- `audit-head`: prints the newest `audit_log` row as `<id>:<hash>` (read-only; `1` when the chain is broken or the log is empty).
- `audit-verify [<id>:<hash>]`: verifies the hash chain and the optional anchor (read-only; `0` intact, `1` broken).
- `verify-signatures`: hashes every signed entry again, and every photo file under `UPLOADS_DIR`, and compares them with what was recorded (read-only; `0` intact, `1` mismatch).
- `prune-access-records`: deletes the rows of `access_log` and `audit_request_context` older than 12 months.

Every command exits `2` on wrong usage and `3` when it **could not run** (database unreachable, schema missing or not current): `3` is neither "intact" nor "broken", and an unattended check must treat it as a failure.

```bash
# first administrator (refused as soon as an active administrator exists)
fly ssh console -C "java -cp /app/app.jar cz.stavebni.denik.cli.AdminCliKt create-admin alice 'Alice Novakova'"

# the only administrator is locked out or forgot the password: new temporary password, all sessions end, a login lockout is lifted
fly ssh console -C "java -cp /app/app.jar cz.stavebni.denik.cli.AdminCliKt reset-password alice"
```

Both `create-admin` and `reset-password` print a generated password once, to standard output only (framework logging is reduced to warnings and errors, which share the terminal); it is stored only as an Argon2id hash, expires after 7 days, the account has to change it at the first login, and the audit log records the action (`user.bootstrap_admin`, `user.password_reset`, with the user's id and the account as it was and as it became) without an acting user and without the password. `create-admin` makes the account a project manager (BOSS) with the administrator flag; further users are created in the application. Exit codes: `0` done, `1` refused (for example an administrator already exists), `2` wrong usage. Locally: `java -cp backend/build/libs/backend-all.jar cz.stavebni.denik.cli.AdminCliKt …` after `./gradlew :backend:shadowJar`.

## Follow-ups

- **Materials, visits and notifications do not exist.** The unreachable `VisitService`, `MaterialService` and `NotificationService` (no routes, no UI, no audit rows or none of the in-transaction locks) and the permissions of the first two were removed, together with the three pieces of the SPA that showed invented data (a dashboard with "Project A" and "Project B", a notification bell with fixed messages, a photo gallery with placeholder photos), none of which was connected to the backend; the tables (`material_needs`, `visits`, `notifications`) are still in the schema. Decision D6 puts them after go-live; when they come back they are written on the audited path (`AuditService.auditedWrite`, project role, locks) from the start, not revived from the old code.
- **Who signed is not frozen.** The signature covers the signer's id. The name and the ČKAIT number that the PDF prints and the signature check returns are read from the user as it is now, so correcting or clearing a ČKAIT number, or renaming a user, changes what every earlier signed entry shows (the audit rows of the user, `user.create` and `user.update`, do record each number as it was, but the PDF and the signature check read the current one). Fix: store both at signing, in a signature format 3 (backlog C2 in [`docs/REVIEW-AND-PLAN.md`](docs/REVIEW-AND-PLAN.md)).
- **ČKAIT and managers (decision D2):** `createProject` adds the site manager it names with their global role instead of BOSS (any BOSS of the project can promote them afterwards), and refuses an unqualified site manager with `400`, not the `409` of the other D2 refusals. An administrator can clear the number of a site manager (signing then refuses, which is safe) and can give themselves a number. The last-manager check counts deactivated and deleted users, and a site manager can be deactivated.
- **Handover protocols:** any member of the project may sign one (`Rbac.kt`), and signing locks it for good (V5). Signing asks for no password and stores no content hash, the protocol has no version for a compare-and-set, and its text fields are not length-checked. Předání a převzetí staveniště is an act of two parties; the plan is one signature for each side.
- **Photos cannot be removed.** `PhotoService.deletePhoto` exists and the matrix allows it to BOSS, but no route calls it, so a photo uploaded to the wrong entry stays there and becomes part of what is signed.
- **Upload memory:** the body of an upload (up to 5 MiB) is read into memory before the access check and before the two-image limit, so many parallel uploads, even from a member who may not upload, can exhaust the heap. A progressive JPEG near the 64-megapixel cap may need several hundred MB to decode (not measured).
- **The PDF of an entry** does not print the authorised persons, the other BOSS and the INSPECTOR members, the handover protocols, or the ČKAIT number next to entries of other parties and acknowledgements (backlog B9), and it prints part A as it stands on the day of the export, not as it was on the day of signing (backlog C2). The photos are listed with the hash of each file, not shown: the PDF has no images. The names of the author, the signer and the other people are read from the users as they are now (see "Who signed is not frozen").
- **The web application on the site:** at phone width the header and the tabs of a project do not wrap, so every page inside the application's layout is laid out wider than the screen (about 570 px with the E2E data) and shrunk to fit. Unsaved text is lost without a warning when leaving the entry through a link inside the application or logging out (closing or reloading the tab asks first), and nothing is kept as a draft. A signed entry is a disabled form with example text in the empty fields instead of a document, and the signer is shown only after "Ověřit podpis". The full list and the order of the work are in [`docs/REVIEW-AND-PLAN.md`](docs/REVIEW-AND-PLAN.md) (backlog, track B).
- **Code without a route, and leftovers:** `DashboardService`, `CsvExportService`, `ValidationService` and `WeatherService` are used only by their tests. The Vite starter files (`frontend/src/App.tsx`, `App.css`, `src/assets/*`, `public/icons.svg`) are not used. `ktor-server-rate-limit`, `ktor-server-sessions`, `ktor-server-call-logging` and `konform` are unused dependencies.
- **Backups are not scheduled and not copied off the machine.** The scripts and the restore drill exist and run in CI (see "Backups and the restore drill"); what is missing is a schedule, an encrypted off-site copy that the application's machine cannot delete from, and a periodic drill against production data. All of it needs the production infrastructure.
- **No second factor.** Signing in rests on a name and a password alone; a leaked or watched-over password gives full access to the diary (and, for an administrator, to user management and the audit log). Rate limits, the password policy and the breached-password check lower the risk and do not remove it. Proposal, not decided: TOTP (RFC 6238) as a second step after the password, with a QR code and a manual key at activation, one-time backup codes stored only as hashes, its own rate limit on code entry, and the secret stored encrypted. Required first for administrators and project managers (BOSS), optional for the rest; a reset by an administrator, audited like a password reset. Its confirmation at signing (decision D8) is a separate question.
- **No per-user volume limit on photo upload and PDF export.** Both are bounded in concurrency (at most 2 images or renders at once; a render that cannot get a slot within 10 s answers `503`) and in size, but one signed-in user can still keep the slots busy. A limit per user and time window (the old application had 60 uploads per 5 minutes and 10 PDFs per 5 minutes) needs no new code in `RateLimiter`: `reserve` without `release` already counts every attempt. The time window does not bound memory, though (see "Upload memory" above): that needs a limit on uploads in flight, taken before the body is read.
- **No monitoring or alerts yet.** Nothing watches uptime, errors, disk or the database; a failed nightly audit-anchor run is the only notification that exists. Needs the production infrastructure (item 13 of [`docs/REVIEW-AND-PLAN.md`](docs/REVIEW-AND-PLAN.md)).
- **Deprecation warnings from the dependency bumps** (not fixed): `Principal` in Ktor (`SessionUser.kt`, and the unused `UserPrincipal` in `Security.kt`), `PartData.FileItem.streamProvider` (becomes `provider()`, keeping the 5 MiB cap) and `dispose` (becomes `release()`) in `PhotoRoutes`, and a `Json {}` built on every call in `ReportRoutes` and `PdfExportService`.
- **Smaller password gaps:** the change-password form does not check breached passwords while typing (the server does, on submit); administrator password resets have no rate limit (only administrators can do them).
